# Security policy

This file is about **reporting** security problems. For how the platform is *designed* to
be safe — the trust boundaries, the catalog-as-trusted-data model, and the rules that
govern future AI/MCP/agent work — see [`docs/security-model.md`](security-model.md).

## Supported versions

The project has **no releases yet**. It is in early development (version `0.1.0`,
unreleased), and only the current `main` branch is supported.

| Version | Supported |
| ------- | --------- |
| `main` (unreleased) | ✅ |
| anything else | ❌ — nothing else has been published |

Once releases begin, this table will list the release lines that receive fixes.

## Current attack surface (be realistic)

As of today the project ships a **static React application** that makes no network
requests, calls no backend, stores no user data beyond a theme preference in
`localStorage`, and generates and executes no commands.

Two components now do more than that:

- `packages/installer` **generates package-manager command strings** from catalog data.
  Nothing executes them — they are text a user pastes into their own terminal — but the code
  that turns data into something a shell will interpret now exists.
- `apps/server` serves a **read-only planning API** and accepts untrusted input at
  `POST /api/plan`. It never executes anything; there is no `child_process` import in the
  workspace and a test asserts there never will be.

There is still no AI layer, no MCP server, no local agent, no database, and no
authentication.

The realistic security issues right now are therefore: **incorrect or malicious catalog
data** (it reaches command generation, so a bad entry is the highest-value target — which is
why identifiers are pattern-checked both in the catalog validator and again immediately
before interpolation), a flaw in the planning API's input validation, dependency
vulnerabilities, supply-chain problems in the toolchain, and the repository's own hygiene.

The design that contains these is in [`docs/security-model.md`](security-model.md). This
policy will be updated as later layers land.

## Reporting a vulnerability

**Do not open a public issue, pull request, or discussion for a suspected vulnerability.**

Report it privately, in either of these ways:

1. **GitHub private vulnerability reporting** — the "Report a vulnerability" button under
   the repository's **Security** tab. Preferred, when enabled.
2. **Email** —
   > **`security@example.com`** — ⚠️ **placeholder.** The repository owner must replace this
   > with a real, monitored address (or enable GitHub private vulnerability reporting and
   > delete this option) before publishing. Until then, contact a maintainer listed in
   > [`MAINTAINERS.md`](MAINTAINERS.md) privately.

Please include:

- What the problem is and why you believe it is a security issue.
- The affected file, package, or endpoint, and the commit you tested.
- Reproduction steps or a proof of concept.
- Your assessment of impact.
- Your environment (OS/distribution, Node and pnpm versions).

**Do not include** live credentials, tokens, personal data, or a working exploit against
anyone else's machine.

### What to expect

The project is maintained by two people in their own time, so please read these as
intentions rather than guarantees:

- Acknowledgement within **7 days**.
- An initial assessment, and a fix or mitigation plan, within **30 days**.
- Public disclosure coordinated with you once a fix is available. You will be credited
  unless you ask not to be.

Please give us a reasonable chance to fix an issue before disclosing it publicly.

## Out of scope

- Reports generated by an automated scanner with no demonstrated impact on this codebase.
- Vulnerabilities in a third-party dependency with no exploitable path here — report those
  upstream; tell us if we should pin or upgrade.
- Missing hardening headers on a static development server.
- Issues that require an attacker to already have local access to the developer's machine.
- Social engineering of maintainers or contributors.

## Handling secrets

- **No secret belongs in this repository.** `.env` files are git-ignored; `.env.example`
  files are committed and contain placeholders only.
- The repository currently declares **no** API keys, tokens, database URLs, or auth
  secrets, because nothing in it implements a feature that needs one. Do not add variables
  ahead of the code that reads them.
- A provider key must never reach the browser bundle — anything in `apps/web` compiled by
  Vite is public. Server-side only, always.
- **If a secret is ever committed, deleting the file is not enough.** The value remains in
  the git history and in every clone and fork. Treat it as compromised: rotate or revoke
  the credential first, then purge the history (`git filter-repo`, or GitHub's support for
  removing sensitive data) and force-push, then tell anyone with a fork or clone to re-clone.
  Rotation is the part that actually fixes it.

## Dependency security

- Dependencies are managed with pnpm and pinned by the committed `pnpm-lock.yaml`. CI
  installs with `--frozen-lockfile`.
- `.github/dependabot.yml` opens grouped update pull requests — weekly for npm
  dependencies, monthly for GitHub Actions. It only takes effect once Dependabot is
  enabled in the repository's settings.
- Run `pnpm audit` locally before adding a dependency, and prefer not adding one at all —
  every runtime dependency in a project that will eventually touch package installation is
  a supply-chain question.
- GitHub Actions are pinned to a major version tag; workflows use the default read-only
  `GITHUB_TOKEN` permissions and never run against untrusted pull-request code with write
  access.

## Catalog data is a security surface

`packages/catalog` is the trusted catalog the project's safety rules refer to. A wrong
identifier there is not a cosmetic bug — it is what a future resolver would act on. Hence:
identifiers must be verified against an authoritative source, no field may ever carry a
command or shell fragment, and provenance (`origin`) must be recorded honestly. See
[`docs/catalog.md`](catalog.md). Report a malicious or dangerously wrong catalog entry
through the private channels above, not in a public issue.
